# arxivjsdata 형식 정의서

- 문서 버전: 1.1
- 대상: ArxivJS 본 앱, `update_summary.js` 같은 보조 도구, 그리고 `arxivjsdata`를 직접 읽거나 쓰는 모든 확장 앱
- 기준 구현: `index.js`, `update_summary.js`, `src/utils/paperId.js`, `src/components/PaperDetail.jsx`

## 1. 목적과 범위

`arxivjsdata`는 ArxivJS가 토픽, 논문 메타데이터, AI 요약, 전문 텍스트 캐시, 하이라이트를 저장하는 파일 기반 저장소다. 데이터베이스 없이 폴더와 파일 이름만으로 관계를 표현하므로, 여러 앱이 같은 폴더를 함께 다루려면 이름 규칙과 파일 형식을 정확히 지켜야 한다.

이 문서는 다음을 정의한다.

- 데이터 루트의 위치와 디렉터리 구조
- 토픽 폴더와 논문 파일의 이름 규칙
- 파일 종류별 형식(`.json`, `.md`, `.txt`, `.hlt`, `.bak`)
- 추가, 이동, 삭제 같은 작업이 파일 단위로 어떻게 일어나야 하는지
- 확장 앱이 지켜야 할 호환성 규칙과 알려진 레거시 예외

이 문서는 HTTP API 명세가 아니다. API 이름은 해당 작업이 파일에 어떤 영향을 주는지 설명하려고 참고로만 적는다.

### 1.1 규범 용어

이 문서에서 **반드시(MUST)**, **해서는 안 된다(MUST NOT)**, **권장(SHOULD)**, **비권장(SHOULD NOT)**, **선택(MAY)** 은 RFC 2119의 의미를 따른다.

- **작성기(writer)**: `arxivjsdata`에 파일을 만들거나 바꾸거나 지우는 앱
- **판독기(reader)**: `arxivjsdata`를 읽기만 하는 앱

## 2. 용어

| 용어        | 의미                                                                      |
| ----------- | ------------------------------------------------------------------------- |
| 데이터 루트 | `arxivjsdata` 디렉터리 자체                                               |
| 토픽        | 논문을 묶는 단위. 데이터 루트 바로 아래의 디렉터리 하나에 해당한다        |
| 토픽 폴더명 | 디스크에 있는 디렉터리 이름 (예: `Agentic_AI`)                            |
| 토픽 표시명 | UI와 API에 쓰는 이름 (예: `Agentic AI`)                                   |
| 논문        | 토픽 폴더 안에 있는 `<paperId>.json` 파일 하나와, 이름이 같은 부속 파일들 |
| paperId     | 논문 파일들이 공유하는 파일명(확장자 제외)                                |
| 논문 번들   | 같은 paperId를 쓰는 `.json`, `.md`, `.txt`, `.hlt`, `.bak` 파일 묶음      |

## 3. 데이터 루트 위치

ArxivJS는 실행 방식에 따라 데이터 루트를 다르게 고른다 (`index.js`의 `dataPath`).

| 실행 방식                                    | 데이터 루트                             |
| -------------------------------------------- | --------------------------------------- |
| 웹 서버 (`npm run server`, `npm run dev` 등) | `<프로젝트 루트>/arxivjsdata`           |
| Electron 데스크톱 앱                         | `<app.getPath('userData')>/arxivjsdata` |
| `update_summary.js`                          | 항상 `<프로젝트 루트>/arxivjsdata`      |

- Electron의 `userData` 경로는 OS와 앱 이름에 따라 정해진다. 예를 들어 Windows에서는 보통 `%APPDATA%\<앱 이름>\arxivjsdata`다.
- 서버가 실행 중이면 `GET /server-info` 응답의 `dataPath`로 실제 경로를 확인할 수 있다.
- 확장 앱은 데이터 루트 경로를 하드코딩하지 않고, 설정으로 받거나 `/server-info`로 알아내는 것을 **권장**한다.

## 4. 디렉터리 구조

```text
arxivjsdata/                         # 데이터 루트
├── userprompt.txt                   # 필수: 요약 프롬프트 템플릿
├── .git/, .gitignore, ...           # 선택: 점(.)으로 시작하는 항목은 무시됨
├── <기타 루트 파일>                 # 선택: 무시됨 (예: 백업 프롬프트, lint 스크립트)
├── <TopicFolder>/                   # 토픽 (디렉터리 하나 = 토픽 하나)
│   ├── <paperId>.json               # 필수: 논문 메타데이터 (이 파일이 있어야 논문으로 인정됨)
│   ├── <paperId>.md                 # 선택: AI 요약
│   ├── <paperId>.txt                # 선택: PDF 전문 텍스트 캐시
│   ├── <paperId>.hlt                # 선택: 요약 하이라이트
│   └── <paperId>.bak                # 선택: 요약 백업 (재생성 직전 또는 삭제한 요약)
└── <AnotherTopic>/
    └── ...
```

규칙:

1. 데이터 루트 아래 디렉터리 중 이름이 `.`으로 시작하지 **않는** 것은 모두 토픽으로 취급한다.
2. 이름이 `.`으로 시작하는 항목(예: `.git`)은 판독기와 작성기 모두 **반드시** 무시해야 한다. 데이터 루트는 git 저장소로 관리될 수 있다.
3. 데이터 루트에 있는 일반 파일 중 `userprompt.txt`만 의미가 있다. 나머지 파일은 무시한다.
4. 토픽은 한 단계만 있다. 토픽 폴더 안의 하위 디렉터리는 정의되어 있지 않으며, 작성기는 이를 만들어서는 **안 된다**.
5. 같은 논문이 여러 토픽에 동시에 있을 수 있다. 이 경우 각 사본은 서로 독립적인 논문으로 취급한다.

## 5. 루트 파일: `userprompt.txt`

| 항목       | 규칙                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| 필수 여부  | **필수**. 파일이 없으면 ArxivJS 서버는 시작 직후 종료한다                         |
| 인코딩     | UTF-8 텍스트                                                                      |
| 자리표시자 | `{context}`. 요약할 때 이 자리에 논문 전문 텍스트가 들어간다                      |
| 치환 방식  | JavaScript `String.prototype.replace`를 쓰므로 **첫 번째** `{context}`만 치환된다 |

- 프롬프트에는 `{context}`를 정확히 한 번 넣는 것을 **권장**한다.
- 이 프롬프트가 `.md` 요약의 구조를 결정한다(8.2절 참고). 확장 앱이 요약을 만들 때도 같은 파일을 쓰는 것을 **권장**한다.
- 다른 이름의 프롬프트 파일(예: `userprompt-20260331.txt`)은 사용자가 보관용으로 둔 것이므로 앱은 이를 무시한다.

## 6. 토픽 폴더

### 6.1 표시명과 폴더명

토픽은 표시명과 폴더명이라는 두 가지 이름을 가진다. 변환 규칙은 다음과 같다.

```js
// 표시명 정규화: '_'를 공백으로 바꾸고, 연속 공백을 하나로 줄인 뒤 앞뒤 공백 제거
function normalizeTopicDisplayName(name) {
  return String(name || '').replace(/_/g, ' ').replace(/\s+/g, ' ').trim();
}

// 표시명 -> 폴더명: 정규화한 뒤 공백을 '_'로 바꿈
function toTopicFolderName(name) {
  return normalizeTopicDisplayName(name).replace(/\s+/g, '_');
}

// 폴더명 -> 표시명
function toTopicDisplayName(folderName) {
  return normalizeTopicDisplayName(folderName);
}
```

예시:

| 표시명               | 폴더명               |
| -------------------- | -------------------- |
| `Agentic AI`         | `Agentic_AI`         |
| `Zero-Shot Learning` | `Zero-Shot_Learning` |
| `AI Healthcare`      | `AI_Healthcare`      |

- 표시명에서는 `_`와 공백을 구분하지 않는다. 그래서 `_`가 들어간 표시명은 표현할 수 없다.
- 확장 앱은 폴더명을 만들 때 **반드시** 위 변환 규칙을 써야 한다. 그렇지 않으면 본 앱이 같은 토픽을 찾지 못한다.

### 6.2 허용 문자

정규화한 표시명은 **반드시** 다음 정규식을 만족해야 한다.

```text
^[a-zA-Z0-9가-힣 ()-]+$
```

- 허용: 영문 대소문자, 숫자, 한글 완성형 음절(가–힣), 공백, `(`, `)`, `-`
- 허용하지 않음: `.`, `/`, `\`, `_`(표시명에서는 공백으로 바뀜) 등 그 밖의 모든 문자
- 이름 비교는 대소문자를 구분한다. 다만 Windows와 macOS의 기본 파일시스템은 대소문자를 구분하지 않으므로, 작성기는 대소문자만 다른 토픽을 만들어서는 **안 된다**.

### 6.3 토픽 수준 동작

| 작업      | 파일시스템에서 일어나는 일                                                                               |
| --------- | -------------------------------------------------------------------------------------------------------- |
| 생성      | `mkdir <폴더명>`. 같은 폴더가 이미 있으면 실패(409)                                                      |
| 이름 변경 | `rename <이전 폴더명> <새 폴더명>`. 대상 폴더가 이미 있으면 실패(409). 폴더 안 파일 이름은 바뀌지 않는다 |
| 삭제      | 폴더가 **완전히 비어 있을 때만** `rmdir`. 파일이 하나라도 있으면 실패                                    |
| 목록      | 토픽은 표시명 기준 `localeCompare`로 정렬한다                                                            |
| 논문 수   | 폴더 안 `.json` 파일 개수(확장자 비교는 대소문자 무시)                                                   |

참고: 토픽을 삭제하려면 `.bak`, 고아 `.txt` 같은 파일까지 모두 지워야 한다. 앱 화면에서는 논문이 0개로 보여도 이런 파일 때문에 삭제가 실패할 수 있다.

## 7. paperId와 파일 이름 규칙

### 7.1 새 paperId 만들기

새 논문을 저장하는 작성기는 **반드시** 논문 제목으로 만든 slug를 paperId로 써야 한다.

```js
function slugifyPaperTitle(title) {
  return String(title || '')
    .toLowerCase()               // 1. 소문자로 변환
    .replace(/[^a-z0-9]+/g, '_') // 2. 영숫자가 아닌 문자열을 '_'로 바꿈
    .replace(/_+/g, '_')         // 3. 연속된 '_'를 하나로 줄임
    .replace(/^_+|_+$/g, '');    // 4. 앞뒤 '_' 제거
}
```

예: `Learning Activation Functions to Improve Deep Neural Networks`
→ `learning_activation_functions_to_improve_deep_neural_networks`

- slug에는 `[a-z0-9_]`만 들어간다. 그래서 모든 OS에서 안전한 파일 이름이 된다.
- slug는 **저장하기 전에 정리한** 제목으로 계산한다. 정리 규칙은 공백을 하나로 줄이고 앞뒤 공백을 지우는 것이다(8.1절의 `title` 참고).
- 본 앱 구현(`getPaperStorageId`)은 논문 객체에 `id`가 있으면 그 값을 slug보다 먼저 쓴다. 그래서 `.json` 안에 `id`를 저장해서는 **안 된다**(8.1.3절).

### 7.2 기존 paperId 읽기: 파일 이름이 기준이다

- 논문의 paperId는 **`.json` 파일 이름에서 확장자를 뺀 값**이다. 판독기는 **반드시** 이 값을 기준으로 삼아야 하고, 제목으로 slug를 다시 계산해서 파일을 찾아서는 **안 된다**.
- 기존 데이터에는 7.1절 규칙과 맞지 않는 레거시 paperId가 있다(12절). 판독기는 이런 파일도 **반드시** 정상 논문으로 다뤄야 한다.
- 작성기가 기존 논문의 부속 파일(`.md`, `.txt`, `.hlt`)을 만들 때는 **반드시** 기존 `.json`의 paperId를 그대로 써야 한다.

### 7.3 충돌과 예외

| 상황                                                  | 결과와 규칙                                                                                                                                                                                        |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 토픽에서 제목의 slug가 같은 두 논문              | 파일 이름이 같으므로 나중에 저장한 논문이 앞의 것을 덮어쓴다. 작성기는 저장하기 전에 같은 파일이 있는지 확인하는 것을 **권장**한다                                                                 |
| 제목에 영문/숫자가 하나도 없음 (예: 한글만 있는 제목) | slug가 빈 문자열이 되어, 그대로 두면 파일 이름이 `.json`이 된다. 작성기는 이 경우 slug로 저장해서는 **안 되며(MUST NOT)**, 사용자가 입력한 paperId를 써야 한다. 입력값은 그 자체로 slug 형식이어야 한다(`slugifyPaperTitle(id) === id`, 비어 있지 않음). 본 앱은 요청 본문의 `paperId` 필드로 이 값을 받고, 값이 없거나 형식이 틀리면 `400`과 `code: "PAPER_ID_REQUIRED"`로 거부한다. 제목 slug가 비어 있지 않으면 `paperId`는 무시한다 |
| 서로 다른 토픽에서 paperId가 같음                     | 정상이다. paperId는 토픽 안에서만 유일하면 된다                                                                                                                                                    |

### 7.4 부속 파일 확장자

| 파일                                | 역할             | 필수                            | git 추적(기본 `.gitignore`) |
| ----------------------------------- | ---------------- | ------------------------------- | --------------------------- |
| `<paperId>.json`                    | 메타데이터       | **필수**                        | 추적                        |
| `<paperId>.md`                      | AI 요약          | 선택                            | 추적                        |
| `<paperId>.txt`                     | 전문 텍스트 캐시 | 선택                            | 제외                        |
| `<paperId>.hlt`                     | 하이라이트       | 선택 (`.md`가 있어야 의미 있음) | 제외                        |
| `<paperId>.bak`                     | 요약 백업        | 선택                            | 제외                        |

- `.json`이 없는 부속 파일은 **고아 파일**이다. 본 앱 화면에는 보이지 않는다. 판독기는 고아 파일을 무시해야 **하고(MUST)**, 작성기는 고아 파일을 만들어서는 **안 된다(SHOULD NOT)**.
- 확장자는 소문자로 쓴다. 토픽의 논문 수를 셀 때는 대소문자를 무시하지만, 논문 목록 API(`getPapers`)는 `.json`과 정확히 같은 경우만 읽는다. 따라서 작성기는 **반드시** 소문자 `.json`을 써야 한다.

## 8. 파일 형식

모든 텍스트 파일은 **UTF-8**로 저장하고 BOM을 붙이지 않는다(**SHOULD NOT**). 줄바꿈 문자는 LF와 CRLF를 모두 읽을 수 있어야 한다.

### 8.1 `<paperId>.json` — 논문 메타데이터

JSON 객체 하나로 이루어진다. 본 앱은 `JSON.stringify(paper, null, 2)`로 저장한다(들여쓰기 2칸, 끝에 줄바꿈 없음). 작성기도 같은 서식을 쓰는 것을 **권장**한다. 그래야 git diff가 깔끔하게 유지된다.

#### 8.1.1 예시

(값은 설명용이며 일부 축약되었다.)

```json
{
  "title": "A Comprehensive Survey of Foundation Models in Medicine",
  "authors": "Wasif Khan, Seowung Leem, Kyle B. See",
  "year": 2024,
  "url": "http://arxiv.org/abs/2406.10729v2",
  "abstract": "Foundation models (FMs) are large-scale deep learning models ...",
  "citation": 42,
  "source": "arxiv"
}
```

#### 8.1.2 필드 정의

| 필드        | 타입              | 필수     | 설명                                                                                                                                           |
| ----------- | ----------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`     | string            | **필수** | 논문 제목. 공백 문자열을 공백 하나로 줄이고 앞뒤 공백을 지운 값(`replace(/\s+/g, ' ').trim()`). 비어 있으면 안 된다. paperId를 만드는 기준이다 |
| `authors`   | string            | **필수** | 저자 목록 문자열. `"First Last, First Last"`처럼 `", "`로 구분한다. 공백 정리 방식은 `title`과 같다. 배열이 아니라 **문자열**이다              |
| `year`      | integer           | **필수** | 출판 연도(예: `2024`). JSON 숫자로 저장한다. 판독기는 숫자 형태의 문자열(`"2024"`)도 받아들이는 것을 **권장**한다                              |
| `url`       | string            | 조건부   | 원문 위치. `source`별 의미는 8.1.4절을 참고한다. 값이 없으면 빈 문자열 `""`이 들어갈 수 있다                                                   |
| `abstract`  | string            | 선택     | 초록. 빈 문자열이거나 필드가 없을 수 있다. 판독기는 없으면 `""`로 다룬다                                                                       |
| `citation`  | integer ≥ 0       | 선택     | 인용 수. **필드가 없으면 "아직 모름"** 이라는 뜻이다. `0`(인용 없음)과 다르다                                                                  |
| `source`    | string enum       | 선택     | `"arxiv"`, `"pdf"`, `"manual"` 중 하나. 없거나 알 수 없는 값이면 `"arxiv"`로 해석한다. 새로 저장할 때는 반드시 넣는 것을 **권장**한다          |
| `dateAdded` | string (ISO 8601) | 예약     | 현재 본 앱은 쓰지 않는다. 논문을 이동할 때 충돌을 비교하는 데만 읽는다(9.3절)                                                                  |
| `date`      | string (ISO 8601) | 예약     | `dateAdded`의 대체값. 동작은 같다                                                                                                              |

#### 8.1.3 저장 금지 필드

다음 필드는 API 응답을 만들 때 서버가 계산해서 붙이는 값이다. 작성기는 이 필드를 `.json`에 저장해서는 **안 된다**.

| 필드            | 이유                                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------------------- |
| `id`            | paperId는 파일 이름에서 정해진다. 저장되어 있으면 `getPaperStorageId`가 이 값을 먼저 써서 파일 이름이 어긋날 수 있다 |
| `hasSummary`    | `.md` 파일이 있는지로 계산한다                                                                                       |
| `hasHighlights` | `.hlt` 파일이 있는지로 계산한다                                                                                      |

#### 8.1.4 `source`별 규칙

| `source` | 의미                                        | `url` 규칙                                                                                 | 전문 텍스트를 얻는 방법                             |
| -------- | ------------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| `arxiv`  | arXiv에서 가져온 논문                       | arXiv abs URL. 예: `http://arxiv.org/abs/2310.16485v2`, `https://arxiv.org/abs/2502.03731` | `url`의 `/abs/`를 `/pdf/`로 바꿔 PDF를 내려받는다   |
| `pdf`    | 외부 PDF URL로 추가한 논문                  | **필수**. 바로 내려받을 수 있는 PDF URL                                                    | `url`을 그대로 내려받는다                           |
| `manual` | 파일 업로드나 텍스트 붙여넣기로 추가한 논문 | 선택. 참고용 URL만 담고, 내려받는 데는 쓰지 않는다                                         | **`.txt` 캐시만 쓸 수 있다.** 다시 만들 방법이 없다 |

- `source`가 없는 레거시 레코드는 모두 `arxiv`로 간주한다.
- `manual` 논문의 `.txt`는 캐시가 아니라 **유일한 원본**이다. 작성기는 이 파일을 지워서는 **안 된다**(8.3절).

#### 8.1.5 알 수 없는 필드와 확장 필드

- 판독기는 모르는 필드를 **반드시** 무시해야 한다.
- `.json`을 고치는 작성기는 **반드시** read-modify-write 방식을 써서, 자신이 모르는 필드도 그대로 남겨야 한다. 본 앱도 인용 수를 갱신할 때 이 방식을 쓴다.
- 확장 앱이 자체 필드를 추가할 때는 다른 앱과 이름이 겹치지 않도록 `x_<앱이름>_` 접두사를 붙이는 것을 **권장**한다(예: `x_mytool_tags`). 접두사가 없는 새 최상위 필드 이름은 이후 이 명세가 쓰도록 예약해 둔다.

### 8.2 `<paperId>.md` — AI 요약

| 항목      | 규칙                                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 형식      | Markdown(UTF-8)                                                                                                                  |
| 생성      | `userprompt.txt`의 `{context}`에 전문 텍스트를 넣은 프롬프트를 LLM(Gemini 또는 Ollama)에 보내고, 받은 응답을 **그대로** 저장한다 |
| 존재 의미 | 파일이 있으면 `hasSummary = true`다. 내용이 비어 있어도 마찬가지다                                                               |

구조는 강제하지 않는다. 다만 기본 프롬프트와 뷰어는 다음 관례를 전제로 한다.

- 첫 줄: `# <논문 제목>`
- 둘째 줄: 저자 목록(일반 텍스트)
- 본문: `##` 섹션(예: Problem to Solve, Key Contributions, Methodology, Results, TL;DR)
- 목차는 `#`, `##`, `###` 제목으로 만든다.
- 수식은 MathJax 문법을 쓴다. 인라인은 `$...$`, 블록은 `$$...$$`. 수식을 백틱으로 감싸지 않는다.
- 데이터 루트의 `.markdownlint.json`, `run-lint.*`는 사용자가 쓰는 lint 설정이다. 형식 규칙에는 포함되지 않는다.

`.md`를 다시 쓰는 작성기는 다음을 지켜야 한다.

- 요약을 다시 생성할 때 기존 `.md`가 있으면 **먼저** `<paperId>.bak`으로 복사한 뒤 덮어쓰는 것을 **권장**한다. 본 앱은 이전 백업을 덮어쓰므로 백업은 한 세대만 남는다.
- `.md` 내용이 바뀌면 `.hlt` 하이라이트가 더 이상 맞지 않을 수 있다. 맞지 않는 하이라이트는 다음에 읽을 때 정리된다(8.4절). 작성기가 바로 정리하는 것도 허용한다(**MAY**).

### 8.3 `<paperId>.txt` — 전문 텍스트 캐시

| 항목      | 규칙                                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 형식      | 일반 텍스트(UTF-8). PDF에서 `pdf-parse`로 뽑은 텍스트이거나 사용자가 붙여넣은 텍스트                                             |
| 생성 시점 | 요약이나 채팅에 전문이 처음 필요할 때 `arxiv`/`pdf` 논문의 PDF를 내려받아 만든다. 또는 사용자가 텍스트를 직접 넣었을 때 저장한다 |
| 읽기      | 파일이 있고 내용이 비어 있지 않으면 PDF를 다시 내려받지 않고 이 파일을 쓴다. 빈 파일은 없는 것으로 취급한다                      |
| 삭제      | `arxiv`/`pdf`: 언제 지워도 다시 만들 수 있다. `manual`: **지워서는 안 된다**                                                     |

- 원본 PDF 파일 자체는 `arxivjsdata`에 저장하지 않는다. 작성기도 PDF를 저장해서는 **안 된다(SHOULD NOT)**.

### 8.4 `<paperId>.hlt` — 하이라이트

JSON 형식이다.

```json
{
  "version": 1,
  "highlights": [
    { "text": "Dying ReLU 문제", "color": "sun" },
    { "text": "학습 가능한 활성화 함수", "color": "sky" }
  ]
}
```

| 필드                 | 타입    | 규칙                                                                                     |
| -------------------- | ------- | ---------------------------------------------------------------------------------------- |
| `version`            | integer | 현재 `1`. 판독기는 모르는 버전이면 파일을 고치지 않는 것을 **권장**한다                  |
| `highlights`         | array   | 하이라이트 목록. 배열이 아니면 빈 목록으로 취급한다                                      |
| `highlights[].text`  | string  | 강조할 텍스트. 공백 문자열을 공백 하나로 줄이고 앞뒤 공백을 지운 값. 비어 있으면 안 된다 |
| `highlights[].color` | string  | 색 이름. 아래 표의 값 중 하나여야 한다                                                   |

색 값(`src/components/PaperDetail.jsx`의 `HIGHLIGHT_COLORS`):

| 값       | 표시색    |
| -------- | --------- |
| `sun`    | `#fff3a3` |
| `amber`  | `#ffd8a8` |
| `rose`   | `#ffc9de` |
| `mint`   | `#c3fae8` |
| `sky`    | `#b3e5fc` |
| `violet` | `#d0bfff` |
| `stone`  | `#dee2e6` |

하이라이트가 유효하려면 다음 조건을 모두 만족해야 한다(`sanitizeHighlights`).

1. `text`와 `color`가 모두 비어 있지 않다.
2. 같은 `text`(정규화한 값 기준)는 한 번만 나온다. 중복되면 앞의 것만 남는다.
3. `text`가 **요약을 렌더링한 표시 텍스트**의 부분 문자열이다. 표시 텍스트는 다음 순서로 만든다.
   - `.md`에서 `$$...$$`, `$...$` 수식을 공백으로 바꾼다
   - `marked`로 HTML을 만든다
   - 블록 태그 경계를 공백으로, 나머지 태그는 지우고, HTML 엔티티를 디코드한다
   - 공백을 정규화한다

   따라서 수식 안의 텍스트나 Markdown 기호(`**`, `#` 등)를 포함한 텍스트는 하이라이트할 수 없다.

동작 규칙:

- `.hlt`는 `.md`가 있을 때만 의미가 있다. `.md`가 없으면 하이라이트 API는 404를 돌려준다.
- 본 앱은 하이라이트를 **읽을 때도** 위 조건으로 정리한 결과를 파일에 다시 쓴다. 그래서 GET 요청만으로도 `.hlt`가 바뀌거나 지워질 수 있다.
- 유효한 하이라이트가 하나도 없으면 `.hlt` 파일을 **지운다**. 빈 `highlights` 배열을 담은 파일을 남기지 않는다.
- 저장 서식은 `JSON.stringify(obj, null, 2)`다.
- 지금 서식에서는 하이라이트가 텍스트로만 식별되므로, 같은 문장이 요약에 여러 번 나오면 그 모두가 강조된다.

### 8.5 백업 파일

요약 백업은 `<paperId>.bak` 하나뿐이며, 논문마다 한 세대만 남는다.

| 만들어지는 때                                 | 내용                                       |
| --------------------------------------------- | ------------------------------------------ |
| 요약을 다시 생성해 기존 `.md`를 덮어쓰기 직전 | 이전 `.md`를 복사한 것(이전 `.bak`은 덮어씀) |
| 사용자가 요약을 삭제할 때                     | 삭제한 `.md`를 이름만 바꿔 옮긴 것(이전 `.bak`은 지워짐) |

- 작성기는 요약 백업을 **반드시** `<paperId>.bak`으로 만들어야 한다.
- 예전 버전이 만든 `<paperId>.md.bak`이 남아 있을 수 있다(12절). 판독기는 이것도 요약 백업으로 알아보는 것을 **권장**하며, 작성기는 이 이름으로 새 파일을 만들어서는 **안 된다**.
- 백업 파일은 논문 목록에 영향을 주지 않는다. 하지만 토픽을 삭제할 수 없게 만든다(6.3절).

## 9. 작업별 파일시스템 동작

확장 앱이 같은 작업을 하려면 본 앱과 같은 결과를 내야 한다.

### 9.1 논문 추가

1. 메타데이터의 `title`과 `authors` 공백을 정리하고 `source`를 정한다.
2. 7.1절 규칙으로 paperId를 만든다.
3. `<topic>/<paperId>.json`을 저장한다.
   - arXiv 검색 결과를 저장하는 경로(`POST /papers/:topic`)는 기존 파일을 **덮어쓴다**.
   - arXiv URL로 추가하는 경로(`POST /paper-by-url`)는 같은 파일이 이미 있으면 **아무것도 하지 않는다**.
4. (선택) `citation`이 없으면 백그라운드에서 인용 수를 조회한다. 값을 얻으면 `.json`을 다시 읽어 `citation`만 바꿔서 저장한다.
5. PDF 또는 수동으로 추가하는 경로(`POST /save-pdf-paper`)는 `.json`과 `.md`를 함께 저장하고, 전문 텍스트가 있으면 `.txt`도 저장한다. 이 경로는 토픽 폴더가 **이미 있어야** 한다.

### 9.2 요약 생성

1. `.txt` 캐시가 있으면 쓰고, 없으면 `source` 규칙에 따라 전문을 얻은 뒤 `.txt`에 저장한다.
2. `userprompt.txt`의 `{context}`를 전문으로 치환해서 LLM에 보낸다.
3. 응답이 끝나면 기존 `.md`를 `.bak`으로 복사하고(이전 `.bak`은 덮어씀), 새 요약을 `.md`에 쓴다.
4. 응답이 중간에 실패하면 `.md`를 바꾸지 않는다.

### 9.3 논문 이동 (토픽 A → 토픽 B)

대상 토픽에 같은 paperId의 `.json`이 **없으면**, `.json`, `.md`, `.hlt`, `.txt`를 이름 그대로 옮긴다(rename).

대상 토픽에 같은 paperId가 **있으면**, 두 `.json`의 `dateAdded`(없으면 `date`, 둘 다 없으면 epoch)를 비교한다.

- 옮길 논문이 더 최신이면:
  - `.json`은 대상의 것을 덮어쓴다.
  - `.md`는 수정 시각(mtime)이 더 최신인 쪽을 남긴다.
  - `.hlt`는 남은 `.md`와 짝이 맞는 쪽을 남긴다.
  - `.txt`는 원본에 있으면 대상의 것을 덮어쓴다. 원본에 없으면 대상의 것을 그대로 둔다.
- 그렇지 않으면 원본 토픽의 `.json`, `.md`, `.hlt`를 지우고 대상은 그대로 둔다.
  - `.txt`는 대상에 이미 있으면 원본의 것을 지운다. 대상에 없으면 원본의 것을 대상으로 옮긴다.

`.txt`는 원본 토픽에 남기지 않는다. `manual` 논문에서는 `.txt`가 유일한 전문 원본이므로, 확장 앱도 **반드시** 위 규칙대로 옮겨야 한다.

어느 경우든 원본 토픽의 백업 파일(`<paperId>.bak`, 레거시 `<paperId>.md.bak`)은 옮기지 않고 **지운다**. 대상 토픽에 이미 있던 백업 파일은 건드리지 않는다. 따라서 이동이 끝나면 원본 토픽에는 그 paperId의 파일이 하나도 남지 않는다.

### 9.4 논문 삭제

`<paperId>.json`, `.md`, `.hlt`, `.txt`를 지운다. 없는 파일은 무시한다. 백업 파일(`.bak`, 레거시 `.md.bak`)은 남는다.

### 9.5 요약 삭제

1. 기존 `<paperId>.bak`을 지운다.
2. `<paperId>.md`를 `<paperId>.bak`으로 이름을 바꾼다.
3. `<paperId>.hlt`를 지운다.

`.json`과 `.txt`는 그대로 둔다.

### 9.6 인용 수 갱신

`.json`을 읽고, `citation`만 정수로 바꾼 뒤 다시 저장한다. 다른 필드는 건드리지 않는다.

## 10. 동시 접근과 무결성

`arxivjsdata`에는 잠금(lock)이나 트랜잭션이 없다. 본 앱 서버, Electron 창 여러 개, `update_summary.js`, 확장 앱이 같은 폴더에 동시에 접근할 수 있으므로 작성기는 다음을 지키는 것을 **권장**한다.

1. **원자적 쓰기**: 같은 디렉터리에 임시 파일을 쓴 뒤 `rename`으로 바꿔치기한다. 임시 파일 이름은 `.`으로 시작하고 인식되는 확장자로 끝나지 않게 한다(예: `.<paperId>.json.tmp`). 그래야 다른 판독기가 읽지 않는다. 쓰기가 끝나면 임시 파일을 반드시 지운다.
2. **짧은 read-modify-write**: `.json`을 고칠 때는 고치기 직전에 다시 읽는다. 오래 들고 있던 객체를 그대로 쓰지 않는다. 본 앱의 백그라운드 인용 수 갱신도 이렇게 한다.
3. **번들 단위로 다루기**: 이동이나 삭제를 할 때는 같은 paperId의 파일을 모두 함께 처리한다. 일부만 옮겨서 고아 파일을 남기지 않는다.
4. **본 앱이 실행 중일 때**: 서버를 거치는 HTTP API로 작업하는 것이 가장 안전하다. 파일을 직접 쓰는 것은 서버가 꺼져 있을 때나, 읽기 전용 작업에 쓰는 것을 **권장**한다.
5. **git 연동**: 데이터 루트가 git 저장소일 때, 기본 `.gitignore`는 `*.txt`, `*.hlt`, `*.bak`을 제외한다. 이 파일들은 기기 사이에 동기화되지 않을 수 있다고 가정해야 한다. 특히 `manual` 논문의 `.txt`가 그렇다.

## 11. 확장 앱 준수 체크리스트

판독기:

- [ ] `.`으로 시작하는 항목과 루트의 일반 파일(`userprompt.txt` 제외)을 무시한다
- [ ] 토픽 폴더명을 6.1절 규칙으로 표시명으로 바꾼다
- [ ] paperId를 `.json` 파일 이름에서 얻는다(제목으로 다시 계산하지 않음)
- [ ] 레거시 paperId(12절)를 정상 논문으로 처리한다
- [ ] `source`가 없으면 `arxiv`로, `citation`이 없으면 "모름"으로, `abstract`가 없으면 `""`로 해석한다
- [ ] 모르는 JSON 필드를 무시한다
- [ ] `.json`이 없는 고아 부속 파일을 무시한다

작성기(판독기 항목 모두 포함):

- [ ] 토픽 이름이 6.2절의 허용 문자 규칙을 지킨다
- [ ] 새 paperId를 7.1절 slug 규칙으로 만들고, slug가 비면 사용자에게 slug 형식의 paperId를 받는다(7.3절)
- [ ] 기존 논문의 부속 파일은 기존 paperId로 만든다
- [ ] `.json`에 `id`, `hasSummary`, `hasHighlights`를 저장하지 않는다
- [ ] `.json`을 고칠 때 모르는 필드를 남긴다(read-modify-write)
- [ ] 확장 필드에 `x_<앱이름>_` 접두사를 쓴다
- [ ] `title`/`authors` 공백을 정리하고, `year`를 정수로 저장한다
- [ ] `.hlt` 색 값을 정의된 7개 중에서 고르고, 빈 하이라이트 파일을 남기지 않는다
- [ ] `manual` 논문의 `.txt`를 지우지 않는다
- [ ] 이동이나 삭제를 번들 단위로 한다
- [ ] UTF-8, `JSON.stringify(obj, null, 2)` 서식으로 저장한다

## 12. 레거시 데이터와 알려진 불일치

다음은 현재 데이터와 구현에 실제로 있는 예외다. 확장 앱은 이를 견딜 수 있어야 하며, 고칠 때는 본 앱도 함께 고쳐야 한다.

| 항목                                | 내용                                                                                                                                              | 확장 앱 대응                                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| base64 paperId                      | 예전 PDF 저장 경로는 `base64(url)`을 파일 이름으로 썼다(예: `aHR0cDovL2FyeGl2Lm9yZy9hYnMvMjUwMi4wMzczMXYy.txt`). 지금은 고아 `.txt`로만 남아 있다 | 파일 이름이 기준이라는 규칙(7.2절)으로 처리한다. 고아 파일이므로 무시한다 |
| HTML 엔티티가 남은 paperId          | `"`가 `&#34;` 상태일 때 slug를 만들어 `..._34_mind_34_...` 같은 이름이 생겼다. 다른 특수 기호에서도 비슷한 이름이 있다                            | 제목으로 slug를 다시 계산하면 파일 이름과 다르다. 반드시 파일 이름을 쓴다 |
| `source` 없음                       | 레코드 대부분(arXiv 시절 데이터)에 `source` 필드가 없다                                                                                           | `arxiv`로 해석한다                                                        |
| 레거시 `<id>.md.bak`                | 예전 본 앱은 요약을 다시 생성할 때 `<id>.md.bak`을 만들었다. 지금은 `<id>.bak`으로 통일했다                                                        | 요약 백업으로 알아보되 새로 만들지 않는다                                 |
| `update_summary.js`의 캐시 이름     | `.txt` 캐시 이름을 파일 이름이 아니라 **제목 slug**로 정한다. 그래서 레거시 paperId 논문에서는 캐시 이름이 어긋난다                               | 확장 앱은 파일 이름 기준 paperId를 쓴다                                   |
| `update_summary.js`의 데이터 루트   | Electron `userData` 경로를 지원하지 않고, 항상 프로젝트 루트의 `arxivjsdata`를 쓴다                                                               | 3절 참고                                                                  |
